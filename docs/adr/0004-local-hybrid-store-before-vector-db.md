# ADR-0004: 检索存储 — 先本地文件实现（BM25 pickle + numpy 向量），Chroma 延后

日期：2026-11-19 · 状态：已接受

## 约束

- 开发机纯 CPU，知识库规模 ~1 万段（真实语料子集），单进程即可全量内存计算
- 语料分钟级重建（评测要求"改了切块策略就重跑"），希望零迁移成本
- JD 关键词含向量库（Chroma/Milvus/FAISS），但那是工程规模信号，不是本规模的最优解

## 候选方案

1. **本地文件 + 内存索引**（rank-bm25 + numpy 矩阵 + pickle/jsonl 落盘）：零服务依赖、可 diff、可重建
2. Chroma：JD 认可、但引入 onnxruntime 等重依赖，且本规模下纯属"简历表演"
3. FAISS/Milvus：Milvus 需服务进程，明显过重

## 决策

先方案 1 落地完整闭环（含 save/load 与评测），**把向量库留作规模增长后的迁移步**：
`HybridRetriever` 的 BM25/矩阵已抽象为可替换内部件，后续加 Chroma 适配器只需替换 `add/save/load` 三个方法（接口不变），并写一份同口径对比评测证明"本地实现与 Chroma 结果一致"后再切换。

## 代价

- 简历少一个向量库关键词 → 用评测报告中的"混合 vs 单路"消融数据补偿（数据 > 关键词）
- 无持久化服务 → 单机部署即目标形态（docker compose 单容器），符合中小厂真实规模

## 复活条件

知识库 > 5 万段、或多进程/多服务共享索引、或需要元数据过滤查询 → 引入 Chroma 适配器。
